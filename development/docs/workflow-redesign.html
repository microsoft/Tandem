Handoff rule:

Completion is a result boundary. Recovery is an exception.

Do not combine the two. A valid current-role terminal result is the sole normal-completion authority. A missing-result continuation prompt is exception recovery only: it adds no workflow state and no prerequisite to accepting a result.

Agreed September 24: this describes the intended contract, not a claim that the current installation has passed qualification.

Normal path: accept the result and advance

Valid terminal result submitted→Persist and apply exactly once→Advance or hand back to the user

The role/model calls its designated result tool. Tandem checks the current role, request identity and result schema. Durable application remains exactly once; a save failure is reported honestly.

No additional execution-completeness check: do not wait for tool/task settlement, permission resolution, turn-end, idle, quiescence or an independent end certificate. Pending bookkeeping cannot veto a valid result. Permissions and read-only restrictions remain independently enforced, not relabeled as completion checks.

Controlled role dispatch and the one-shot missing-result continuation use explicit native mode: "immediate" with agentMode: "interactive", so attached background work does not strand a successor in native enqueue. Tandem's durable request queue is unchanged. The native runtime owns scheduling, execution and cleanup; Tandem does not reconstruct those semantic states to certify role completion.

Exceptional path: the required result is missing

This path applies only when the owned execution session emits session.idle before the active role has submitted its expected terminal result. It detects a missing submission, not a runtime crash. It is event-driven, not periodic polling.

session.idle + no result→One automatic continuation prompt→Same session, role and request

Ask the agent to continue once

Preserve existing work and context. Ask the same agent to finish any remaining work and submit the designated result. Do not restart the workflow, rerun completed implementation, route a new user request or fabricate a result.

This is an ordinary continuation message, not a health-check ping or a new completion supervisor.

Then use the ordinary result path

If a valid result arrives, accept it through the normal completion path immediately. Recovery does not change what counts as completion.

If the continuation itself reaches session.idle without a result, report the missing result explicitly. No second automatic prompt or unlimited retry loop; duplicate idle notifications are not new attempts.

Stop/Close takes precedence. Do not send a recovery prompt after an accepted result or explicit Stop/Close. Preserve work; report actual native errors and uncertain outcomes honestly rather than silently retrying or claiming success.

Two native idle events with different meanings

Native signalMeaning and Tandem handling
assistant.idleThe main processing loop can be idle while background agents or attached shell commands remain pending. This does not trigger missing-result recovery and is not a completion or failure signal for the role.
session.idleNo background agents or attached shell commands remain in flight. With a missing role result, this triggers the bounded exception path above. It never establishes successful role completion and is never required after a valid result.
Explicit native error or shutdownReport the actual native outcome separately. Missing a result does not prove a crash, and the continuation prompt is not crash recovery.

The installed SDK's generated/session-events.d.ts distinguishes these events. The main-chat idle observation in Main chat & Tandem is a separate queue-wake path, not this active-role recovery path.

How Host distinguishes progress from completion

Structured tool contractWhat it establishes
Submit the internal planIdentifies the planned tasks, dependencies and expected work. Host validates and tracks them; the user need not approve the technical breakdown.
Report task progress or outcomeUpdates the matching task, not the entire plan. Host can show what is running, how many tasks are reported complete and what remains.
Submit final implementation resultA valid result bound to the current role, request and plan establishes the whole-plan completion boundary. Persist and apply it once, then dispatch Review with immediate native delivery without independent execution-end or idle proof. A partial task report, unbound "done" statement or silence is not this terminal result.

These describe contract purposes, not literal tool names. A valid terminal result establishes completion; progress reports do not. Missing-result recovery is a separate one-shot exception path, explained in Completion & recovery.

Example: catch a wrong route early

"The Design specifies single-player play. Adding a second player changes controls, scoring and match outcomes, so I need your direction on the Design before proceeding."

Implementation reports the concern rather than making that product decision. Host states what work, if any, is retained. The user can clarify the request, request Designer work or choose another direction.

Example: a valid Review finding

"Five of six criteria are supported. An actual browser playthrough is still missing. Rules tests and HTTP responses do not establish movement, firing and replay."

The Reviewer raises the issue. The user can request validation or discuss the criterion. The finding alone neither approves the implementation nor forces an autonomous repair loop.

Example: code and Design disagree

"The Design specifies three waves, but the code runs endlessly." Explain the difference so the user can request a Design change or correction of the code.

The Reviewer does not choose which behavior to keep. A completed internal technical plan does not approve changed product intent.

Normal user involvement is not recovery

These conditions can interrupt the main path, but they have different meanings and owners. A single generic "Blocked / Ready" label cannot explain them.

Waiting for a product decision

Designer or Reviewer has delivered an understandable outcome, or Implementation has reported a Design prerequisite. The completed role task has handed back to the user; discussion remains possible.

Do not label this an uncertain execution or require a technical recovery action simply to respond. A Design concern does not automatically start Designer or mean the whole implementation plan is complete.

Waiting for a command permission

The user grants or denies a specific external action. This is separate from internal plan acceptance.

The Host preserves the task and pauses its active execution budget while that owned permission is pending. No timeout penalty for taking time to decide.

A requested Stop

The Host stops the current work and discards requests already queued when Stop is recorded. Keep their original messages in conversation/WAL history, clearly marked discarded; never execute them later.

Keep code changes already made so the user can inspect or continue from them. Later messages are new input, not part of the discarded queue. Existing task-bound cancellation and permission withdrawal protections still apply.

Implementation cannot finish

Explain what was completed, what remains and what input or prerequisite is missing. Do not pretend that a partial plan is the completed implementation.

Return the genuine need for user input rather than silently publishing a whole-plan Review or changing the requested scope.

Required result is missing

On native session.idle without the current role's terminal result, make one automatic continuation attempt in the same session, role and request. If that attempt also ends idle without a result, report the missing result.

This is exception recovery, not a new state boundary. assistant.idle does not trigger it. Valid results complete immediately; Stop/Close prevents a recovery prompt. See Completion & recovery.

Execution outcome is unknown

A failed native send, disconnected runtime or uncertain request owner is different from an idle session missing its result. Preserve the exact uncertainty and do not blindly resend or infer a crash.

The one-shot missing-result path does not authorize general replay, reset or discarded work. Report actual native errors separately; none of these observations adds an execution-end requirement to a valid result.

New input during work

Keep the user's exact message and show its queued status. It must not silently change an active task's scope.

Process the next request at an appropriate owned boundary. Explicit Stop discards the requests already queued but preserves their audit history; messages admitted afterward are new input.

Responsibilities and the intended change

User: Design and code consistency

Judge the intended product Design and whether the implementation consistently follows it. Examine role outcomes, resolve consequential questions, and choose the next direction.

The user is not required to approve a technical list of files, dependencies and implementation tasks or manage internal coding rounds.

Host: deterministic continuity

Own routing admission, internal plan validation, task ordering, permissions, cancellation, durable state, whole-plan Review dispatch and user-facing handoffs.

Agents submit typed results, never arbitrary next-state commands. The Host enforces the transitions shown here.

Agent: ordinary coding within its task

Plan, reason, use permitted tools, implement and test. Internal tasks may be separate bounded calls in the same private session.

If it considers a Design change necessary, report that prerequisite and yield to the user through Host. Do not force a Design change for ordinary code-level decisions. Implementation never rewrites the canonical Design to excuse a mismatch; Reviewer remains the consistency check on completed work.

Changes from the earlier state machine

  • Responsibility colors replace status colors. Every User box is amber; every Host box is blue. Agent roles have separate colors and explicit text labels.
  • One project working copy. Use the existing Copilot session workspace for implementation and Review. Teleos creates no additional editable copy and has no patch-transfer or Apply stage. This does not mean writing directly into a separate repository's main checkout.
  • No human technical-plan approval state. Planning and plan acceptance happen internally under the user's requested work. External command permissions remain separate.
  • No per-item formal Review loop. The Host advances internal implementation tasks until the complete plan is finished. Local tests are not a separate Reviewer stage.
  • Designer and Reviewer both end at the user. Changed Design, unchanged Design, clean Review and Review findings all produce an explicit conversational handoff.
  • Review reports on code that already exists. It does not make edits real or automatically undo them. Preserve whether criteria passed and issues remain; a Review that found no issues is not a guarantee of correctness or user acceptance of the product.
  • No automatic Review-to-fix loop. The user responds to findings; the Router selects the appropriate path for that new instruction.
  • One queue with an explicit answer priority. Show the outcome, handle its current Q&A before ordinary messages, and process each answer envelope alone. Preserve the order of separate answer submissions and the chronological audit. Ordinary text batching resumes when that interaction permits; no arbitrary caller-controlled priority is introduced.
  • Stop is separate. It cancels current work and discards the existing queue; preserve history and code, without automatic rollback.
  • Early Design concerns end at the user too. Implementation may decline the routed work during planning or coding. Host explains why, preserves partial work and waits. There is no automatic Implementation-to-Designer transition.

Private conversation does not require private files

The Host may retain a separate private agent session for controlled instructions and long-lived reasoning context. That session works in the same project working copy used by the user's Copilot session.

Unfinished changes and Review-flagged code are visible in that working copy, as in ordinary coding. The user explicitly chose to keep code changes on Stop. Review reports findings rather than performing a rollback; the user decides the next direction. The Host still distinguishes this task's changes from pre-existing or conflicting edits.

Review snapshots, diffs, immutable evidence and the WAL remain necessary. One editable working copy does not mean one stored version or loss of history.

Technical guarantees remain inside the Host

These are retained engineering constraints, not additional product-policy decisions silently bundled into this round's agreement. Any proposed change to command permissions, deployment policy or outside-edit handling needs separate discussion.

Valid current-role terminal result→Persist and apply exactly once→Advance through immediate native delivery or hand off

No native-end or resource-settlement prerequisite. Correct role/request/schema and durable application remain required; permissions and read-only enforcement remain independent. The one-shot missing-result continuation is exception recovery, not a completion boundary or additional lifecycle state.

One reusable private execution session can serve many sequential role tasks. Retain exact conversation, task identities, immutable evidence and context, while rejecting stale results and unowned inputs.

The central Host WAL remains the authoritative state history. In-memory views are derived from it. Immutable images, code inventories and patches remain referenced evidence; SDK history remains runtime-owned.

One project working copy is not an OS sandbox. The Host enforces permissions and protects against conflicting edits; the native runtime owns execution, scheduling and cleanup. Neither internal plan acceptance nor a Review with no issues found silently authorizes deployment, publishing or unrelated external effects.
