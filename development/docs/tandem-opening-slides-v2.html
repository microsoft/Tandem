Opening: Tandem: two minds, one direction. Our question is how a user and an agent can move quickly without moving toward different outcomes.

This is a simplified traditional development path, not a claim that every team works in a waterfall. Requirements, design and test planning describe what should happen before production code is written. Documents may include diagrams and examples, not just prose. Validation then checks the result against those expectations.

The benefit is upfront agreement. The cost is the effort of expressing and reviewing detail before people can see a concrete experience. Iterative teams already revisit these decisions; the tension is how to get useful agreement with less burden.

A code-first or vibe-coding approach starts with a prompt, generates an application, and lets the user inspect and iterate. The low barrier to starting is valuable. This is an approach, not a universal description of all agents or all teams.

Some workflows also generate documentation from what they implemented. That can be useful for understanding the code, but a description of the implementation is not automatically an agreement about what the user wanted.

The user brings product context, team norms and expectations they have not said aloud. The agent brings repository patterns, learned priors and prompt inference. A short prompt can work because much of this overlaps. One important difference can still dominate the outcome.

Here the user expects normal access to stop immediately, with 30 days to recover an accidental deletion. The agent might infer immediate permanent purge. Neither interpretation has yet been confirmed. Both implementations could pass tests written for their own assumptions.

The first result can feel like opening a blind box, or 盲盒. This is not a claim that all generated first versions are slow. Generation may be fast. The cost is discovering a consequential mismatch only after code, integration or review effort has already been spent.

04 / Four ways the gap survives

More output ≠ understanding.

The missing signal is agreement about the outcome.

Feedback arrives late

Concrete reactions come after implementation choices are embedded.

Documents become homework

Long specs make users reconstruct the experience in their heads.

Direction drifts over time

Local changes can lose the original intent across a long task.

Tests can confirm the wrong idea

Unit tests are useful. Shared assumptions still need user validation.

Internal consistency is not the same as shared intent.

Not less rigor / Better evidence of understanding

These are four risks, not inevitable properties of every workflow.

First, delayed concrete feedback. Users may not recognize an assumption until they can see the result. If that happens only after production implementation, correction can involve more than changing a sentence.

Second, review burden. Long specifications make users read, connect details and reconstruct the experience in their heads. That can be as demanding as reviewing code. Journeys, diagrams and interactive previews make the behavior easier to grasp, mismatches easier to spot and feedback more concrete. The point is ease of understanding, not simply producing visuals before producing documents.

Third, long-horizon drift. A succession of locally plausible changes can gradually diverge from the original goal. The remedy is a stable agreement to compare against, not a claim about any newly shipped context or recovery mechanism.

Fourth, test interpretation. Unit tests are essential for checking local behavior. But a purge implementation and purge tests can agree while the user expected recovery. This does not mean the same correctly specified test accepts both. It means tests need expectations grounded in the user's outcomes.

Transition: We want an earlier reviewable experience, without demanding an exhaustive reading assignment.

Stage 1 / Optimize time and effort to agreement—not code generation speed

Tandem's proposal has two distinct stages: prototype to a spec, then build against it. Stage 1 is prototype-led discovery; Stage 2 is iterative, spec-anchored development. We embrace the build-first start without treating generated behavior as agreed intent.

Start with the user's statements, then targeted questions about consequential choices needed for a useful first prototype. Let the user play with it. Their feedback sends us back to clarification, confirmation and refinement as needed. This is a discovery loop, not a one-pass handoff.

Long documents ask users to reconstruct the experience mentally. A concrete prototype, journey or interaction makes behavior easier to understand, a mismatch easier to notice and feedback easier to give. Visuals carry the essential behavior and choices; short complementary notes are optional, not a long document the user must read first. For a non-GUI system, use request sequences, command journeys or concrete output examples.

The original Stage 1 illustration is this Model Y prototype. A short request for a navigatable 3D app becomes a vehicle preview with camera and orbit controls, feedback and a draft feature specification. The screenshot shows Design active with the earlier prototype retained for review. Our two stages are broader than the application's individual tabs. This capture does not establish that every control works or every requirement is accepted.

The first agreed spec synthesizes intent, confirmed scope, assumptions and explicitly open questions. It is neither a conversation transcript nor documentation of whatever code the agent generated. User confirmation establishes intent; prototype behavior alone does not. Prototype code may be reused, revised or replaced before production.

We aim to optimize time and user effort to the first agreed spec, alongside missed expectations and later rework. This is a proposed working model, not a measured speed advantage or a claim that every capability has shipped.

Stage 2 / Enter from Stage 1—or directly with an existing agreed spec

The reason for visual artifacts first is understanding, not just ordering. Show the experience instead of asking users to decode a long specification. A journey reveals the sequence, a diagram exposes relationships, and an interactive preview makes a response tangible. Users can notice a mismatch and point to it rather than translate prose into a mental simulation. Visuals must carry real behavior and decisions, not merely decorate the same long document. Short optional notes explain what the visuals cannot.

This is Stage 2, not the Stage 1 prototype. The first agreed spec now governs implementation and ongoing review. An existing agreed spec may enter here directly after checking scope and gaps; an existing repository without agreed intent is not equivalent. Visuals remain the primary review surface throughout development, with short optional notes.

Use visual journeys, screens, interactions and representations of system behavior. For a non-GUI system, that might be a sequence, a state transition or a concrete request-and-response example. The user should be able to inspect, try, point and react. Notes can support that process, but the user is not required to read prose to participate.

This borrows the linked artifact set from original slide eight. The journey shows what happens after deletion. The timeline makes the exact recovery boundary inspectable: before 30 days is allowed; at and after the deadline is rejected. The decision map separates unresolved legal retention and shared-asset questions from the agreed recovery policy. Recovery expiry does not authorize permanent purge. These are three views of one agreement, not three specifications free to invent different rules.

Compare this with asking the user to reconstruct the same behavior from a long specification. They can point directly to the deadline, the blocked-access step or an unanswered question. That is the reason for visual-first review. The account-deletion policy is illustrative, not a claim about Tandem's own session recovery. A proposed change still requires the user's decision; a rendering alone does not establish agreement.

Commitment 1: keep the agreement authoritative. When intent changes, update and confirm the affected agreement before implementation. Implementer builds the software and executes and validates the agreed user journeys, including interactions across components. If a helper and its tests both use seven days while the agreement says thirty, Implementer corrects that drift and reruns affected scenarios within the authorized implementation work. Do not rewrite the spec to justify the code.

Reviewer is read-only and has two responsibilities: check implementation conformance to the complete agreed Design, and identify material over-engineering beyond it. Reviewer inspects code and the available evidence; executing the user journeys and fixing ordinary code problems remain Implementer's responsibilities. Review is not a separate general bug hunt or test-coverage audit. Reviewer reports findings and coverage limits; it does not edit code, change Design or authorize another implementation cycle.

Commitment 2: bring consequential decisions back to the user. Even faithful implementation of the existing spec can reveal a missing expectation or unconsidered consequence. Shared files might need to remain available to collaborators, for example. Do not invent a default. Pause affected work, make the question explicit, obtain a user decision, and confirm any change to the agreement before continuing. Known conflicts and open questions can need user judgment just as newly discovered gaps can.

Agreement is not a document we produce once and forget. The artifacts anchor implementation and review. Different views should express the same agreement, not become separate specifications that silently contradict one another.

Implementer's validation follows the user's story across relevant components as well as local units. For this illustrative agreement, normal access is blocked immediately, recovery is possible before 30 days, and recovery is rejected at and after the deadline. Check these outcomes against the agreed boundaries and disclose anything that could not be exercised. Unit tests remain useful; they are one part of the evidence, not proof that every user expectation is satisfied.

Recovery expiry does not by itself authorize permanent purge. Legal retention and shared assets can still require decisions. Be explicit about the scope supported by evidence and what remains open.

When Review reveals a gap, conflict or consequential question, bring it back to the user. Record the decision and update the agreement if appropriate. If the code simply drifted, propose correcting the implementation, not rewriting the agreement to make that code appear right. A Change Design choice goes to Designer; a Change implementation choice proposes implementation against the agreed Design. Mixed choices go to Designer first. In every case, another implementation cycle requires explicit user confirmation before Planner or code changes.

The loop is iterative, not an automatic repair loop: agreement, authorized implementation and story-driven validation, then read-only Review and a user decision where needed. Review ends with a consolidated report and any findings or limitations; it is not user approval. Only a newly authorized implementation cycle performs further corrections and reruns affected scenarios before another Review. Internal fixes during an already authorized implementation cycle do not require a separate confirmation for each edit.

This deck describes a working model and direction, not a claim that every supporting product capability has shipped. It does not announce recovery, compaction or rename functionality.

Close: Make intent visible before implementation, keep it anchored during implementation, and validate it through user outcomes. Two minds, one direction.
